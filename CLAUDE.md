# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Custom plugin repository for **Noctalia Shell** — a Linux desktop shell for Wayland compositors. Plugins are written in **QML/JavaScript** using the **Quickshell** framework and loaded directly at runtime (no build step, no test suite, no linter).

## Commands

```bash
# Update registry.json from all manifest.json files
node .github/workflows/update-registry.js

# Format QML files before committing
/usr/lib/qt6/bin/qmlformat -i <file>.qml

# Hot reload during development
NOCTALIA_DEBUG=1 qs -c noctalia-shell
```

## Language Policy

All documentation, code comments, commit messages, README files, and inline text in this repository must be written in **English**. Plugin-internal planning docs (in `*/docs/`) are excluded from this rule as they are gitignored and never published.

## Architecture

### Plugin Layout

Each plugin is a top-level directory with a `manifest.json` (required). Standard entry points:

- **`Main.qml`** — IPC handler and data layer; receives `pluginApi` property
- **`BarWidget.qml`** — status bar widget; receives `screen`, `widgetId`, `section` properties
- **`Panel.qml`** — popup panel; must expose `contentPreferredWidth/Height`, `allowAttach`, and `geometryPlaceholder`
- **`Settings.qml`** — settings UI; must implement `saveSettings()` function
- **`i18n/*.json`** — translations; `en.json` is the reference

### Registry

`registry.json` is auto-generated by GitHub Actions on push to `main` when `**/manifest.json` or the registry script changes. Never edit manually.

### Design Documents

`taskwarrior/docs/PLAN.md` contains the complete Taskwarrior plugin specification (architecture, component details, hook system, i18n keys). `taskwarrior/docs/IMPLEMENTATION.md` has the 17-task implementation plan. Always consult these before implementing Taskwarrior plugin features.

## Quickshell Framework Patterns

### pluginApi

All components receive `property var pluginApi: null` from the framework:

```qml
pluginApi.mainInstance              // Access Main.qml from Panel/BarWidget/Settings
pluginApi.panelOpenScreen           // Screen where panel is open
pluginApi.openPanel(screen)         // Open/close/toggle panel
pluginApi.closePanel(screen)
pluginApi.togglePanel(screen)
pluginApi.pluginSettings            // Persisted settings object
pluginApi.saveSettings()            // Persist after modifying pluginSettings
pluginApi.manifest                  // manifest.json contents
pluginApi.tr(key, interpolations?)  // Translation with {placeholder} replacement
pluginApi.trp(key, count, singular?, plural?, interpolations?)  // Plural forms
```

### Process + StdioCollector (async CLI execution)

```qml
Process {
    id: myProcess
    command: ["task", "export"]
    stdout: StdioCollector {
        onStreamFinished: { let data = JSON.parse(text); /* ... */ }
    }
    stderr: StdioCollector {}
    onExited: function(exitCode, exitStatus) { /* ... */ }
}
// Start: myProcess.command = [...]; myProcess.running = true;
```

### IPC Handler

```qml
IpcHandler {
    target: "plugin:<plugin-id>"
    function myMethod(param: string) { /* IPC params are always strings */ }
}
// External call: qs -c noctalia-shell ipc call plugin:<id> myMethod "param"
```

### Settings Pattern

```qml
// Local state copies with defaults from manifest
property var cfg: pluginApi?.pluginSettings || ({})
property var defaults: pluginApi?.manifest?.metadata?.defaultSettings || ({})
property string mySetting: cfg.mySetting ?? defaults.mySetting

function saveSettings() {
    pluginApi.pluginSettings.mySetting = mySetting;
    pluginApi.saveSettings();
}
```

### Versioning & Release

#### SemVer Rules (`MAJOR.MINOR.PATCH`)

| Bump  | When                                                                 | Example                                     |
|-------|----------------------------------------------------------------------|---------------------------------------------|
| PATCH | Bug fixes, security fixes, typos, purely cosmetic changes           | `1.0.0` → `1.0.1`                          |
| MINOR | New features, new settings, new i18n keys (backward-compatible)     | `1.0.1` → `1.1.0`                          |
| MAJOR | Breaking changes: removed settings, changed IPC interfaces, incompatible hook changes | `1.1.0` → `2.0.0` |

**Required:** Every PR that modifies plugin code (QML, JS, hook scripts) **MUST** include a version bump. Without a version bump, users will not receive the update.

#### Source of Truth

`<plugin>/manifest.json` → `"version"` is the **single authoritative source** for the plugin version. All other references are derived from it.

#### Version Bump Checklist

The following files **must** be updated with **every** version bump:

1. **`<plugin>/manifest.json`** — Set the version field to the new version (source of truth)
2. **`README.md`** — Update the plugin table so the displayed version matches manifest.json
3. **`registry.json`** — Generate with `node .github/workflows/update-registry.js` (never edit manually)

**IMPORTANT:** The plugin table in `README.md` MUST be updated with every version bump. Inconsistencies between manifest.json and README are not acceptable.

#### Release Order

```
1. manifest.json   — Bump version
2. README.md       — Update plugin table
3. Registry        — node .github/workflows/update-registry.js
4. Commit          — chore(<plugin>): bump version to X.Y.Z
```

The registry is also automatically regenerated by a GitHub Action on push to `main`, but running it manually before committing ensures the PR diff is complete and reviewers see the correct registry.

### Pull Request Workflow

1. **Create a feature branch** — `feat/<name>` or `hotfix/<name>`, ideally in a git worktree (`.worktrees/`)
2. **Implement** — Commits in `type(scope): message` format
3. **Bump version** — Update `manifest.json` `version` per SemVer (required for plugin code changes)
4. **Format QML** — Run `/usr/lib/qt6/bin/qmlformat -i` on all changed `.qml` files
5. **Create PR** — `gh pr create` with summary, security fixes (if applicable), and test plan
6. **Wait for automated review** — Gemini Code Assist reviews automatically
7. **Evaluate review feedback** — Review technically, do not blindly accept. Push back with reasoning on incorrect suggestions. Incorporate valid findings.
8. **Trigger re-review** — After incorporating feedback, repeat the full review cycle:
   - Commit and push fixes
   - Reply to all inline comments in the PR thread (what was fixed, with commit hash)
   - Post `/gemini review` as a PR comment to trigger a new review
   - Wait for and evaluate new feedback
   - Repeat the cycle until no open findings remain
9. **Merge** — Only when the last review cycle produces no new findings. Squash merge preferred for a clean history on `main`.

**IMPORTANT:** After every push of fixes, a re-review MUST be triggered with `/gemini review`. Never merge without a final review pass. The cycle is: Fix → Push → Reply to comments → `/gemini review` → Evaluate feedback → Repeat if needed → Merge.

### Security Patterns (Taskwarrior Plugin)

- **CLI commands as arrays** — never use `sh -c` with string concatenation, always use parameterized arrays: `["task", arg1, arg2]`
- **rc.hooks=0** — on all read-only `task` commands to prevent feedback loops with on-exit hooks. CRUD actions keep hooks enabled.
- **Debounce on IPC handlers** — Use timer with `restart()` instead of direct execution to debounce burst calls
- **Input validation** — UUID format (RFC 4122), field whitelist for modify, tag regex, priority enum (H/M/L)
- **$HOME expansion** — Always resolve tildes in paths via subprocess, never store as `$HOME` literal
